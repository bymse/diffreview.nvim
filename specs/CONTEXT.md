# Context: Local Review Comments

## Issue Summary

The plugin currently persists changed-file progress but has no comment records, editing interface, or comment presentation. Reviewers need local feedback that survives review restart and file changes without being lost when a line no longer matches.

## Final Goal

Reviewers write line and consecutive-line-range comments on current-file text, including unchanged text; file-list entries and non-text review views support file-level notes, including deleted files. Comment records and locations have no side field; the side-by-side UI rejects old-pane creation and maps eligible locations to current-file lines. Comments persist with stable identities and `status: 'open'|'resolved'|'stale'`, can be edited, deleted, resolved, and reopened, appear as virtual text where displayable, and remain discoverable in a separate comment quickfix list when stale or when no changed files remain. The changed-file and comment quickfix lists remain independent but occupy the same bottom drawer one at a time. `ReviewComment` opens a temporary editor showing the target location and current code separately from the editable body; writing commits and acknowledges available stale locations, closing without writing discards changes, and empty saved text deletes an existing comment. There is no manual reattachment, automatic relocation, publishing, Markdown export, automatic refresh, comment creation outside the displayed review, or inline-mode enablement.

## Key Design Decisions

- Structured review state is authoritative; editor buffers, extmarks, and quickfix lists are disposable projections. Save a candidate checkpoint before exposing a successful comment mutation; a failed save must leave both active state and presentation intact.
- Keep the existing Git-specific `diffreview-nvim` storage location and exact repository/source/baseline/target identity, including the current distinction between worktree and explicit-target reviews. Move the checkpoint schema forward in place without migration; the user assumes there are no old checkpoints to preserve. Persist only local comment fields, with no remote IDs or publication status.
- A text comment has a stable file ID, fixed inclusive current-file line bounds, and an SHA-256 hash of the selected lines joined with newline separators. On explicit refresh or restart, compare only the same range in the same file identity: changed text or unavailable locations make unresolved comments stale; matching text restores open status. Neighbors, duplicate matches elsewhere, and line movement do not relocate comments. A file-level note remains open while its file identity is present. Resolved comments stay resolved regardless of location availability; reopening rechecks the stored hash or file identity and assigns open or stale. Resolved text comments are presented at file level rather than implying a valid line attachment.
- Writing a stale comment, even an unchanged `:w` or `:wq`, captures the current text hash at its retained range and assigns open if the location is available. Body and metadata persist atomically before adoption. Missing file identities, absent/non-text current content, or out-of-range bounds retain stale status and the previous hash while permitting body edits; ranges are never clamped or retargeted. Such comments remain manually deletable. Genuine content-read failures and snapshot mismatches reject the write rather than acknowledging uncertain code. Writing resolved comments preserves resolved status and metadata.
- Checkpoint version 4 stores side-free comments with one status enum, an `anchor_hash` for text records, and no duplicated display path or captured lines/neighbors. Retained file-progress records supply current or last-known browsing paths; comments without a matching retained record fall back to their file ID. Older checkpoint versions are unsupported without migration, consistent with the existing no-old-checkpoints assumption. A per-review `Comments` instance exposes explicit add/edit/delete/resolve/reopen methods; session mutations operate on a fork and save the complete candidate before adopting it. The active instance and checkpoint projection share the same adopted records, not independently mutable collections.
- `ReviewComment` uses a visual line selection if given, the current review line otherwise, or the selected changed-file quickfix row for a file-level note; non-text views use file-level location. Saving empty content deletes an existing comment; new empty content creates nothing. An unsaved editor prevents manual refresh until saved or closed. Stop/close must not silently discard uncommitted text.
- Keep two separately owned native quickfix lists, not a combined list. Only one appears in the bottom drawer; commands switch or toggle the lists. Resolved comments remain visible with status. The comment list supports navigation, editing, deletion, and resolution toggling; the `a` mapping, `ReviewCommentAttach`, pending-attachment state, and reattachment APIs are removed.
- Text editor previews are pinned to the comparison from which they were opened. New text writes must also match the originally previewed range, so restoring unsaved source edits cannot acknowledge unseen snapshot text. Refreshing that comparison requires reopening a text editor before saving. Editor writes wait for asynchronous capture and persistence before native close-on-write proceeds; failed writes retain the draft, including unchanged-buffer `:wq` failures. By-ID text-editor opening and stale text edits use coroutine-based snapshot loading.
- Keep old or renamed file identity as defined by the diff collector. Files outside the changed-file list and other unfinished UI modes are excluded. Where a file or side cannot be rendered as text, a file-level note is still available when the review view presents that file.
- Correctness risks: worktree text may change between diff load and comment save; content reads and refresh reconciliation must use a consistent comparison snapshot or reject a mismatched candidate. Native quickfix history is global; ownership, mappings, and drawer switching must not operate on an unrelated list.

## Codebase Map

- `lua/diffreview/init.lua` registers public review commands and delegates to the configured session; `lua/diffreview/review.lua` owns start, stop, selected-file loading, manual refresh, state updates, and UI callbacks.
- `lua/diffreview/review_progress.lua` defines `ReviewProgress`/`ReviewIdentity` and reconciles persisted file records with current diffs; `lua/diffreview/storage.lua` validates and atomically replaces per-identity JSON checkpoints.
- `lua/diffreview/diffs/init.lua` provides `load_diffs`, `load_selected_view_model`, stable file IDs, per-file fingerprints, storage path and review identity; `lua/diffreview/diffs/content.lua` represents old/current snapshot or path-backed text. A file fingerprint encodes more than text and cannot substitute for context matching.
- `lua/diffreview/ui/init.lua` owns the review tab, presentation callbacks and separate file/comment quickfix IDs. `lua/diffreview/ui/quickfix/files_list.lua` owns file ordering, presented-row validation and selection mappings; `lua/diffreview/ui/quickfix/comments_list.lua` owns comment rows, validation and key-to-named-callback mappings. `lua/diffreview/ui/quickfix/helpers.lua` supplies shared native-list ownership, selection, drawer, cursor and formatting operations without list-specific state. The session receives named operations rather than raw keys and retains mutation guards, status decisions and asynchronous orchestration. `lua/diffreview/ui/comment_editor.lua` owns pinned acwrite drafts and write/cleanup lifecycle.
- `lua/diffreview/ui/side_by_side.lua` owns old/current windows, scratch/path-backed buffers and cleanup, and exposes validated displayed views. `lua/diffreview/ui/comment_presentation.lua` consumes those views for comment rendering, navigation and displayed-text validation; `lua/diffreview/ui/comment_decorations.lua` renders valid ranges, file notes and stale file-level annotations. `lua/diffreview/ui/decorations.lua` renders diff extmarks. The UI-owned `lua/diffreview/ui/decoration_tracker.lua` tracks decorated buffers per namespace, clears all tracked review decorations on presentation changes/cleanup, and clears only the comment namespace on comment updates.
- `tests/integration/storage_tests.lua`, `tests/integration/review_progress_tests.lua`, and `tests/integration/review_refresh_tests.lua` cover checkpoint and refresh behavior against real Git fixtures; `tests/integration/ui/quickfix_tests.lua` covers quickfix ownership. `tests/functional/user_commands_test.lua` and `tests/helpers/functional_review.lua` cover command-driven editor behavior. Register new suites in `tests/integration/init.lua` or `tests/functional/init.lua`.
- `AGENTS.md` requires LuaLS, formatting, and affected-part tests; `justfile` provides `just lint`, `just format`, `just format-check`, and `just test`. Use lowercase snake_case test names and real editor/Git fixtures; functional tests cover key-driven behavior, integration tests cover module interfaces.
