# Spec 001: Load Lightweight Review Files

## Goal

Implement the diffs module interface that resolves the approved Git comparison and returns lightweight changed-file summaries plus private metadata for future lazy loading, without creating or retaining any full file snapshots.

## Prerequisites

None.

## Context

Read `specs/CONTEXT.md` for the comparison policy, stable identity rules, module responsibilities, deferred behavior, and relevant codebase map.

## Tasks

1. Move `lua/diffreview/ui/diff_view_model.lua` to `lua/diffreview/diff_view_model.lua` and update affected annotations or module references. Preserve the existing full-model aliases and fields for current side-by-side UI consumers, but do not add full-model construction or snapshot loading. Delete the old module path without a compatibility shim because no current runtime consumer requires it.
2. Preserve the shared `ChangedFileViewModel` contract with `id: string`, `display_path: string`, `added_lines: integer`, `removed_lines: integer`, and `viewed: boolean`. Diffs loading initializes `viewed` to false; future review behavior may mutate it, but Git-derived loading must not own persisted reviewed state.
3. Implement `diffreview.diffs.load_review` in `lua/diffreview/diffs/init.lua` with the coroutine-only interface `load_review(options: DiffLoadOptions): DiffLoadResult, LoadedDiffs|nil`. `DiffLoadOptions` is a required table containing only optional `cwd: string`, `from: string`, and `to: string`. `DiffLoadResult` has `ok: boolean` and `error: DiffLoadError|nil`; `DiffLoadError` has `kind: 'invalid_options'|'repository'|'missing_default_branch'|'revision'|'git'|'filesystem'`, `message: string`, and optional `detail: string` for low-level diagnostics. Success returns `{ ok = true, error = nil }` plus `LoadedDiffs`; failure returns `{ ok = false, error = ... }` plus nil.
4. Define `LoadedDiffs` with the public field `files: ChangedFileViewModel[]` and private repository plus `entries_by_id: table<string, LoadedDiffEntry>` state. Each `LoadedDiffEntry` retains its summary and either the original `GitDiff` record or an untracked relative path plus inspected binary/count metadata. The retained state must not contain snapshot lines, `DiffFileContent`, `DiffFileVersion`, or a `DiffViewModel` map.
5. Reject non-table options, unknown keys, non-string or empty-string values, and a `to` revision without `from` as `invalid_options`. Treat an omitted `cwd` as the process current directory. A nonexistent, non-directory, or inaccessible `cwd` is a `filesystem` error; an accessible directory that is not inside a Git worktree is a `repository` error; untracked-file inspection failures are `filesystem` errors. Preserve a concise stable message for users and place raw Git or filesystem diagnostics only in `detail`.
   - Use one stable message per error kind: `Invalid diff load options`, `Not inside a Git worktree`, `Default branch is unavailable`, `Unable to resolve revision`, `Git operation failed`, and `Unable to inspect repository files` for `invalid_options`, `repository`, `missing_default_branch`, `revision`, `git`, and `filesystem`, respectively.
   - A repository with no commits follows the requested comparison path: zero revisions fail as `missing_default_branch` when `origin/HEAD` is absent, while a supplied revision or a required `HEAD` that cannot resolve to a commit fails as `revision`.
   - An absent, invalid, or non-commit `origin/HEAD` is `missing_default_branch`. An unresolved or ambiguous caller-supplied revision, unresolved required `HEAD`, or merge-base failure such as unrelated histories is `revision`. Repository discovery failure after filesystem validation is `repository`. Diff/list command failures and malformed Git output are `git`. Keep raw command or filesystem diagnostics in `detail` for every non-validation failure except when no diagnostic exists.
6. Extend `lua/diffreview/diffs/git.lua` and reuse `lua/diffreview/diffs/parsers.lua` as needed to classify local and remote branch refs separately from tags and object-ID expressions, resolve commits, and compute merge bases. Explicit or unambiguously resolved refs under `refs/heads/` and `refs/remotes/` are branches; refs under `refs/tags/` and object-ID expressions are exact commits; ambiguous Git names fail as `revision` errors instead of applying a guessed precedence. Two supplied revisions always resolve to exact commit endpoints even when a revision names a branch.
   - Resolve an explicit full ref only in its named namespace. For shorthand names, probe exact candidates under `refs/heads/<name>`, `refs/remotes/<name>`, and `refs/tags/<name>` without using Git's implicit precedence; one candidate determines classification, and multiple candidates are ambiguous. If no named-ref candidate exists, resolve the input as a commit-ish expression such as `HEAD`, an object ID, or an ancestry expression and classify it as an exact commit. Zero matches or a non-commit result is unresolved. For two-revision comparisons, perform the same ambiguity check but treat every successfully resolved result as an exact endpoint.
7. Implement the comparison matrix exactly: zero revisions require `origin/HEAD`, compute its merge-base with `HEAD`, and compare that baseline through the current working state; one branch revision computes its merge-base with `HEAD` and compares through the current working state; one non-branch commit-ish revision uses the exact commit as baseline and compares through the current working state; two revisions compare exact commits and exclude later worktree, index, and untracked changes.
8. For working-state comparisons, combine the existing tracked Git diff with paths from `GitRepo:ls_files`. Classify and count each untracked file using Git numstat semantics against an empty source: numeric additions identify text, while `-` counts identify binary content. An empty text file has zero additions, a non-empty final unterminated line counts, and line-ending style does not add an extra line; expose zero additions and removals for binary summaries. Unreadable, missing-during-load, or otherwise uninspectable paths fail the load with a `filesystem` error. Do not retain untracked contents after inspection.
   - Obtain tracked staged and unstaged changes with one baseline-to-working-state Git diff, matching the existing `GitRepo:diff(from)` behavior. Do not concatenate separate index and worktree diffs or double-count a path; normalize the single resulting record and then append separately discovered untracked paths.
9. Normalize tracked and untracked records directly into `ChangedFileViewModel` values without introducing a mapper module. Added, copied, and untracked records use `new:<current-path>`; records with baseline identity use `stored:<old-path>`, including modified, deleted, renamed, and type-changed records. Unmerged records use `stored:<old-path>` when their parsed old mode or object ID indicates baseline presence and otherwise use `new:<current-path>`. Display the current path when it exists and the old path for deletions.
10. Retain enough private per-ID metadata to support a later `load_diff(file_id)` implementation, including old/current paths, old/new object IDs and modes when available, operation/status, similarity information, repository root, and current absolute path when applicable. Do not implement or expose `load_diff` in this phase.
11. Add `tests/integration/diffs_load_review_tests.lua`, register it in `tests/integration/init.lua`, and extend `tests/helpers/git_repo.lua` only where reusable repository fixtures are required. Cover required-table and field validation, zero-argument default-branch success and absence, one-argument local and remote branches, tags and hashes, ambiguous and unresolved revisions, two exact endpoints, repositories without commits, tracked staged/unstaged changes, untracked text line-ending categories, untracked binary and filesystem failures, empty comparisons, and every parsed operation category.
   - The complete parsed operation categories are added (`A`), copied (`C`), deleted (`D`), modified (`M`), renamed (`R`), type-changed (`T`), and unmerged (`U`); untracked is a separate loader category discovered through `ls-files`.
12. Assert the status-to-summary rules explicitly: added and copied paths receive new IDs; deleted paths display and identify the old path; modified and type-changed paths retain stored IDs; renamed paths display the destination while identifying the source; unmerged identity follows actual baseline presence; and untracked paths receive new IDs. Also assert that two-endpoint comparisons exclude working-state changes, binary summaries remain format-safe for quickfix, every summary starts unviewed, errors have the required kind/message/detail invariants, and `LoadedDiffs` plus each `LoadedDiffEntry` contain no snapshot or full-model fields. Extend parser unit coverage only if new wire formats or parser behavior are introduced.
13. This phase intentionally remains one cohesive implementation unit as approved in `PLAN.md`: model relocation, comparison resolution, summary normalization, retained lazy-load metadata, and real-Git integration proof together establish one loader contract. The implementer may organize work incrementally, but must complete the full final verification budget before returning; do not split or defer part of the public contract. `entries_by_id` is prescribed as the private stable-ID seam required by the approved future lazy-loading boundary, not as a public storage abstraction.
